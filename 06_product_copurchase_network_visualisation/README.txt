# Online Retail Product Co-Purchase Network Analysis

## Project Overview

This project develops a relational visual analytics workflow to explore product co-purchase patterns in the Online Retail II transaction dataset.

The original data is stored as a transaction table in which each row represents a product recorded within an invoice. Python is used to clean the transaction data, construct customer baskets, generate repeated product-product relationships, and export weighted node and edge tables for Gephi.

The resulting graph is modelled as a weighted, undirected product co-purchase network:

```text
Node        -> Product / StockCode
Edge        -> Two products purchased in the same invoice
Edge Weight -> Number of invoices containing the product pair
```

Gephi is then used for interactive network exploration, force-directed layout, degree-based hub analysis, modularity-based community detection, and comparison of network density at different co-purchase thresholds.

The project focuses on identifying:

- product hubs
- repeated co-purchase relationships
- product communities
- dense and peripheral network structures
- scalability and visual clutter in large relational datasets

---

## Project Objectives

The analysis addresses the following questions:

1. How can transaction-level retail data be transformed into a product co-purchase network?
2. Which products act as highly connected hubs?
3. What product communities are visible in repeated co-purchase behaviour?
4. Which product pairs have the strongest repeated relationships?
5. How does edge-weight filtering affect network readability?
6. How effectively can node-link visualisation support exploration of large relational datasets?

## 3. Basket Construction

A customer basket is defined using the invoice identifier.

Only unique products within each invoice are retained before basket construction:

```python
basket_df = clean_df[["Invoice", "StockCode"]].drop_duplicates()
```

Products are then grouped by invoice:

```text

```

Example conceptual basket:

```text

    ↓

```

The resulting basket contains four unique products.

### Basket Filtering

Only baskets containing at least two products are useful for generating product-product relationships.

The workflow retains baskets with:

```text
Minimum ProductCount: 2
Maximum ProductCount: 50
```

The upper limit reduces the influence and computational cost of exceptionally large baskets that would generate a very large number of pair combinations.

Final valid baskets:

```text

```

The basket dataset is exported to:

```text

```

Product lists are stored using a pipe-separated format:

## 4. Product Pair and Edge Construction

For every valid basket, Python generates all possible combinations of two products.

For a basket containing:

```text
A
B
C
```

the generated product pairs are:

```text
A-B
A-C
B-C
```

Python uses:

```python
from itertools import combinations
```

Each product pair is sorted before counting so that:

```text
A-B
```

and:

```text
B-A
```

are treated as the same relationship.

This produces an undirected network.

Repeated product pairs are counted across invoices.

The workflow generated:

```text
2,076,826 unique product pairs
```

The edge table contains:

| Field | Description |
|---|---|
| Source | First product StockCode |
| Target | Second product StockCode |
| Type | Undirected |
| Weight | Number of invoices containing the pair |

The complete edge table is exported to:

```text
data/processed/all_product_edges.csv
```

## 5. Node Construction

Node files contain products that appear in the corresponding filtered edge network.

Each product node contains:

| Field | Description |
|---|---|
| Id | Product StockCode |
| Label | Product description |
| TotalQuantity | Total units recorded after cleaning |
| TotalRevenue | Quantity multiplied by Price |
| InvoiceCount | Number of unique invoices containing the product |
| Degree | Number of connected products |
| WeightedDegree | Sum of co-purchase edge weights |

Product revenue is calculated as:

```text
Revenue = Quantity × Price
```

### Degree

Degree represents the number of unique products connected to a node.

A high-degree product is co-purchased with a wide variety of other products.

### Weighted Degree

Weighted degree is the sum of the edge weights connected to a product.

It reflects the overall repeated co-purchase strength associated with the node.

## Gephi Network Model

The network is defined as:

```text
Weighted
Undirected
Product Co-Purchase Network
```

### Nodes

```text
Products / StockCodes
```

### Edges

```text
Products appearing in the same invoice
```

### Edge Weight

```text
Number of invoices in which the product pair appears together
```

The graph is undirected because co-purchase is mutual.

For example:

```text
Product A purchased with Product B
```

represents the same relationship as:

```text
Product B purchased with Product A
```

### ForceAtlas2

The threshold-100 network is arranged using ForceAtlas2.

Project configuration:

```text
Scaling:               2.0
Gravity:               1.0
Edge Weight Influence: 1.0
```

ForceAtlas2 is used because the product network does not have a fixed hierarchy.

Connected products are positioned closer together based on network structure.

Node coordinates generated by ForceAtlas2 are layout positions and should not be interpreted as original business variables.

---

### Noverlap

Noverlap is applied after ForceAtlas2.

Purpose:

```text
Reduce node overlap
Improve node visibility
Improve hub readability
```

Noverlap is used separately from the main force-directed layout.

The communities represent structural groups of products that are more densely connected through repeated co-purchase relationships.

They may suggest:

- product families

However, community interpretation requires business context and should not be treated as causal.

## Threshold Comparison

| Network | Threshold | Nodes | Edges | Main Finding |
|---|---:|---:|---:|---|
| Threshold-100 | >= 100 | 581 | 1,948 | Cleaner and more readable |
| Threshold-30 | >= 30 | 1,653 | 20,065 | Dense hairball effect |

The comparison demonstrates a direct trade-off between:

```text
relationship coverage
        vs
visual interpretability
```

Lowering the threshold retains more relationships but greatly increases visual clutter.

The threshold-100 network is therefore more appropriate for focused visual analysis.

## Analytical Interpretation

The visual analysis suggests a network with:

- visible product communities
- high-degree hub products
- strong repeated product relationships
- dense central structures
- smaller peripheral groups

Product hubs may act as structural anchors because they are co-purchased with a wider range of products.

Strong weighted edges identify product pairs that repeatedly appear in the same invoices.

However:

```text
High Degree != High Profitability
Co-Purchase != Causality
ForceAtlas2 Position != Business Value
```

A central product is not automatically the most profitable product.

Products may appear together because of:

- promotions
- seasonality
- stock availability
- pricing
- customer behaviour
- product themes

The results should therefore be treated as exploratory network evidence rather than causal business conclusions.

---

## Scalability

Node-link diagrams become less readable as graph density increases.

The project demonstrates this through the two filtered networks:

```text
Threshold 100
581 nodes
1,948 edges
        ↓
Readable network structure

Threshold 30
1,653 nodes
20,065 edges
        ↓
Dense hairball effect
```

For larger relational datasets, potential strategies include:

- stronger edge filtering
- aggregation
- community detection
- ego-network analysis
- interactive filtering
- adjacency matrices
- network sampling

An adjacency matrix may outperform a node-link graph for dense networks because it avoids extensive edge crossing.

However, node-link diagrams remain intuitive for visually exploring:

- hubs
- communities
- connectivity
- peripheral structures

## Analytical Limitations

The project has several limitations.

The transaction dataset does not provide sufficient context to explain why products were purchased together.

Possible missing factors include:

- promotions
- seasonality
- customer segments
- product margins
- sales channels
- stock availability
- pricing changes

The network is based on invoice-level co-occurrence.

It does not identify sequential purchasing behaviour or causal influence between products.

The basket-size filter and edge-weight thresholds are analytical choices that influence the resulting network structure.

ForceAtlas2 positions are algorithmically generated and do not represent original numerical business variables.

Community detection identifies structural groups but does not automatically provide semantic product-category labels.
